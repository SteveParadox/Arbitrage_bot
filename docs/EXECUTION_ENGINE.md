# Phase 10: Bybit Execution Engine

Phase 10 adds authenticated Bybit V5 spot execution in Rust.

It is deliberately testnet-first and remains gated by Phase 9 risk approval.

## Safety defaults

```env
BYBIT_EXECUTION_TESTNET=true
BYBIT_EXECUTION_MAX_ORDER_NOTIONAL=5
ARB_LIVE_TRADING_ENABLED=false
```

The private client refuses to start against mainnet unless live trading is explicitly enabled.
A mainnet client also requires `ExecutionMode::Live`. A testnet client requires
`ExecutionMode::Testnet`.

The Phase 10 execution cap is intentionally much smaller than the broader Phase 9 research trade
limit.

## Authentication

The current implementation supports Bybit system-generated HMAC API keys.

Authenticated requests use:

```text
X-BAPI-API-KEY
X-BAPI-TIMESTAMP
X-BAPI-RECV-WINDOW
X-BAPI-SIGN
```

The exact signed payload is:

```text
GET:
timestamp + api_key + recv_window + exact_query_string

POST:
timestamp + api_key + recv_window + exact_json_body
```

The API secret is private inside `ExecutionConfig` and is never included in its safe summary.

RSA/self-generated Bybit keys are not implemented in this phase.

## Risk gate

Creating a private order requires:

1. Phase 9 `RiskEngine::evaluate` approval.
2. `prepare_execution` to create a `PreparedExecution`.
3. A second risk-approval validation immediately before the signed order POST.

The second check catches:

- a manual kill switch engaged after initial approval;
- a circuit breaker tripped after initial approval;
- an expired approval;
- a trade-ID mismatch.

Cancellation and read-only monitoring remain available without a fresh approval. This is
intentional: a kill switch should stop new risk, not prevent the system from cancelling existing
risk.

## Spot quantity semantics

For Phase 10, every spot market order explicitly sends:

```text
marketUnit = baseCoin
```

That means:

```text
requested_quantity
filled_quantity
remaining_quantity
```

all use base-coin units.

This avoids Bybit's default spot market-buy behavior where `qty` is quote value, which would make
requested quantity and cumulative executed base quantity incomparable.

The caller must convert the scanner/risk amount into a precision-aligned base quantity before
building `ExecutionOrderRequest`.

## Place order is not fill confirmation

`POST /v5/order/create` returning an order ID only means Bybit accepted the asynchronous request.

The engine therefore records:

```text
PlaceOrderAck
    |
    v
order monitoring
    |
    +-- New
    +-- PartiallyFilled
    +-- Filled
    +-- Cancelled
    +-- PartiallyFilledCanceled
    +-- Rejected
```

A successful execution requires all of:

```text
orderStatus == Filled
remaining_quantity == 0
filled_quantity >= requested_quantity
execution-history quantity confirms cumulative fill
```

## Fill accounting

For each execution record, Phase 10 stores:

```text
execution ID
quantity
price
value
fee
fee currency
maker/taker flag
execution timestamp
```

Multiple fills are sorted and de-duplicated by execution ID.

Average fill price is quantity weighted across executions.

Fees are stored as a map by currency, for example:

```text
BTC  -> 0.0000012
USDT -> 0.0031
```

They are not blindly added together across currencies.

## Retry handling

GET requests use bounded exponential backoff for documented retryable conditions such as:

- HTTP 429 / server errors;
- Bybit server timeout;
- Bybit rate limiting;
- Bybit server errors;
- selected spot backend/network errors.

Create-order retries are more conservative.

After a retryable or duplicate-looking create response, the engine first queries the unique
`orderLinkId`.

If the order exists, it treats that as the original accepted order.

Only when the order cannot be found and the error is retryable may it retry the same
`orderLinkId`.

This reduces duplicate-order risk after ambiguous network failures.

## Cancellation

`cancel_order` sends the Bybit cancel request but does not assume the acknowledgement means the
order is cancelled.

If an order-monitoring timeout occurs and `BYBIT_EXECUTION_CANCEL_ON_TIMEOUT=true`, the engine:

```text
requests cancellation
        |
        v
polls order state again
        |
        v
records final/remaining quantity
```

If the order became terminal before the cancel request completed, cancellation reports
`already_terminal=true`.

## Order monitoring

The correctness baseline in this phase uses authenticated REST polling.

Defaults:

```text
poll interval               50 ms
order timeout             3000 ms
cancel confirmation       2000 ms
fill confirmation         2000 ms
```

Bybit recommends private WebSocket streams for real-time order/execution updates. A later latency
optimization can replace or supplement polling without changing the public execution state model.

## Balance synchronization

`sync_balances` queries the Unified account wallet.

For every coin it captures:

```text
wallet balance
locked balance
spot borrow
equity
USD value
estimated non-leveraged spot available
```

The estimated spot-available value is:

```text
max(wallet_balance - locked - spot_borrow, 0)
```

It is intended for ordinary non-leveraged spot risk checks. It must not be treated as a universal
derivatives/margin transferable-balance formula.

## Execution failure circuit breaker integration

`execute_with_risk_tracking` reports unsuccessful execution outcomes back to Phase 9.

Examples include:

- submission failure;
- monitoring failure;
- timeout;
- cancellation failure;
- rejected order;
- partial-fill cancellation;
- fill-history confirmation failure.

Successful fully confirmed fills call `record_execution_success`.

With the default Phase 9 configuration, three execution failures inside five minutes latch the
execution-failure circuit breaker.

## Current boundary

Phase 10 provides authenticated order primitives and single-order execution monitoring.

It does **not** yet automatically orchestrate all three legs of a triangular route as one atomic
transaction. No exchange provides atomicity across the three independent spot orders, so a future
route executor must explicitly handle leg-to-leg quantity propagation and unwind/recovery policy
when Leg 2 or Leg 3 fails.

That recovery logic should not be hidden inside a generic order client.


## Phase 11 detailed attempt errors

The execution client now also exposes
`execute_with_risk_tracking_detailed`.

A detailed failure carries:

```text
execution stage
optional accepted order acknowledgement
underlying execution error
```

This lets the three-leg coordinator distinguish:

```text
definitive submission rejection
    -> prior exposure may be unwound

accepted order + monitoring/cancel uncertainty
    -> do not send a blind opposite order
    -> engage kill switch
    -> reconcile exchange state first
```

The original `execute_with_risk_tracking` remains available and maps the detailed failure back
to the underlying execution error.
